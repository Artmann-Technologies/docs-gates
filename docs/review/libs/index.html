01The verdict

No — docs-gates imports none of the 23 subjects

The root module carries zero non-stdlib requires, and the one module allowed to depend on third parties, pkg/provider, requires only go-finding v1.15.1 and go-finding/toolsdk v1.16.0. go-error-family v0.12.0 sits in that graph as an indirect dependency whose API is never named. Verified per subject by module-path searches over both modules; the exact commands are in each report's “How to verify” section.

And for every one of the 23, non-adoption is the right call — a justified no

16 subjects are NOT-APPLICABLE: the problem class does not exist in a run-to-completion exit-code CLI. There is no HTTP server, no SSE, no secrets, no database, no event stream, no retry boundary, no file watching and no HTML to render. Each carries a one-line reason on all 236 not-applicable rows.

7 subjects are NOT-ADOPTED: a real overlap is named at file:line, and adoption is barred by the root contract rather than by oversight. Each names the exact condition that would flip it.

The fleet argument still pays — five hardening items, none needing a dependency

The owner's concern is re-implementation debt: if every project rebuilds everything, nobody benefits from collective improvements. This run found almost none of that debt. What it did find are five small fixes that make the battery sturdier and the fleet's shared lessons visible inside docs-gates. They are ranked below.

03Why the root stays stdlib-only

The root module's zero-require contract is deliberate architecture, not neglect. It is what the seven NOT-ADOPTED verdicts are measured against.

docs-gates (root module) 0 non-stdlib requires └── pkg/provider (separate go module, the BuildFlow toolsdk provider) ├── go-finding v1.15.1 ├── go-finding/toolsdk v1.16.0 └── go-error-family v0.12.0 (indirect; API never named)
+
A hermetic build with no dependency churn The nix build needs no vendor hash, so a dependency bump can never break it. scripts/stack-drift-check.sh fails CI on any drift, which keeps the contract enforced rather than assumed.
+
Byte-pinned output as a public contract Fifteen parity invocations are pinned byte-for-byte (internal/battery/parity_test.go). Any output-path change is a deliberate re-pin, so a rendering or error-formatting library has nothing to improve without breaking the contract.
+
An argv API that predates the single binary Five legacy wrapper names are API and still answer --version. A framework rewrite of dispatch or flags would put that surface at risk for no user-visible gain.
+
One legitimate home for third-party code pkg/provider already lives outside the root contract. Every report names it, or a new sibling module in its image, as the first home for any future adoption.

04The fleet argument, answered

“If all my projects re-implement or re-integrate everything, I will only fix bugs all day and none of my projects benefit from collective improvements.” Each report tested that against its library by hunting for hand-rolled equivalents. The findings:

+
No fleet-solved code is being re-implemented, with two named exceptions The Levenshtein suggester exists twice (cmd/docs-gates/main.go:188-247 and cmdguard/pkg/cmdguard/v5/flags_suggest.go:13-84), and writePreservingMode exists three times inside docs-gates itself. Both are 25-line stdlib functions with pinned behavior, below any reasonable sharing threshold.
+
The relationship already runs the other way The fleet consumes docs-gates rather than the reverse. cmdguard's CI runs the battery as its showcase consumer (cmdguard/.github/workflows/ci.yml:191), go-appkit is a pilot consumer with its own benchmark shape (internal/docsfreshness/bench_test.go:145-152), and go-sse and cqrs-htmx run the battery through the PATH wrappers.
+
Sharing already happens at the protocol layer erraudit, which is built on go-error-family, enforces this repo's typed-carrier discipline without an import. go-finding supplies the severity type the provider needs. Sharing the protocol instead of the implementation is the cheaper form of collective improvement here.
+
New capability should arrive as a sibling module that execs the binary Every flip trigger below points the same way: a watch mode, a daemon, a dashboard or an HTTP status endpoint belongs in a nested module built on the right fleet library from day one, with the root staying stdlib-only and its goldens untouched.

05Ranked opportunities

Five findings survived the audit. All are zero-dependency and respect the root contract. Sorted by impact: the two important items first.

Important

1. Panic-guard each gate in the battery

internal/gatecli/gatecli_capture.go:121 · found in httputil.md, echoed in go-health.md

No recover() exists anywhere in docs-gates. A panicking gate would crash the whole docs-gates run process and mask every later gate, contradicting the battery's own contract: every gate runs independently, with no first-failure abort. No gate has panicked to date, which is why this is a hardening item rather than an incident.

Fix A short defer recover() inside the gate-capture wrapper that converts a panic into a named FAIL row for that gate only, so the matrix still prints all rows. Stdlib only; no golden moves on the healthy paths.
Important

2. Suggest the right key when a config key is unknown

internal/config/known_keys.go:3-6 · found in cmdguard.md

An unknown key in .docs-gates.json only earns a WARN today. cmdguard turns the same event into “did you mean …?”, and docs-gates already owns the Levenshtein routine (cmd/docs-gates/main.go:188-247). A typo such as --audit-max for audit_max costs a re-read of the README where it could cost nothing.

Fix Lift the existing Levenshtein into one shared helper and add a suggestion to the unknown-key WARN. About 20 lines and one test, with a payoff on every mis-keyed repository config across the fleet.
Nice to have

3. Collapse the three writePreservingMode copies into one helper

internal/docspurge/docspurge_collect.go:185, internal/docsarchive/docsarchive.go:222, internal/docsstrike/docsstrike.go:146-153 · found in go-atomic-write.md

The same seven-line “write, preserving the file mode” slice is hand-rolled three times. It is the only real duplication the run found, and it is intra-repository, so it needs no library to fix it.

Fix One gatecli helper used by all three sites. Behavior is identical, so no golden moves.
Nice to have

4. Write the CHANGELOG before the TODO_LIST in purge --apply

internal/docspurge/docspurge.go:199-205 · found in go-atomic-write.md

Purge rewrites TODO_LIST first and CHANGELOG second. A crash in that window deletes struck rows whose CHANGELOG bullets never landed: silent ledger loss. Swapping the order leaves a duplicate bullet instead, which is visible and safe to re-purge.

Fix Swap the two writes. Zero dependencies, and the goldens do not pin the write order.
Nice to have

5. Record the torn-write residual as a standing decision

AGENTS.md, the “Deliberate non-fixes” bullet · found in go-atomic-write.md

The four mutator writes are plain os.WriteFile under --apply, with git as the atomicity layer for tracked files. That decision was made once in an archived io-surface report and is not visible where a reader looks for standing decisions.

Fix One line in AGENTS.md next to the existing Truncate entry, so the next audit does not re-derive it.
